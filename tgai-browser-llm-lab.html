Start here — what is TGAI?

TGAI Browser LLM Lab is a local-first AI playground contained in one HTML application. It lets you try browser-ready language models, give them local reference material, experiment with vision-capable chat models, and generate images with a separate browser-local image runtime.

The simple version: this page is the control panel. The AI models are separate, often very large files. TGAI downloads the runtime/model resources it needs, then runs the actual inference on your computer instead of sending each prompt to a hosted AI inference server.

TGAI is meant to make the moving pieces visible rather than hide them. That is why the page exposes model source links, GPU information, cache status, loading progress, generation speed, and a runtime log.

Chat & Reference workspace

This is the language-model side of TGAI. Pick a model, click Load Model, wait for it to download/load, and then chat with it. The model runs through WebLLM, an in-browser language-model engine that uses WebGPU for hardware acceleration.

Chat modelReads your text and produces text. Coding models are tuned more heavily toward programming; general models are broader assistants.
Vision / VLM modelA language model that can also inspect an attached image. A text-only model cannot understand image attachments.
Reasoning modelA model tuned to spend more effort on multi-step problems. It can be slower and may produce longer answers.
Embedding modelTurns text into numeric vectors used to compare meaning. It is useful for search/RAG, not normal conversation.

New Chat clears the conversation history used by TGAI. Unload Model asks the browser runtime to release the active language model from working memory; it does not necessarily erase the downloaded model files from browser storage.

What are local reference files and “grounding”?

You can load local text, SQL, code, JSON, logs, Markdown, CSV and other supported text files into the Reference area. TGAI reads that material in your browser and can insert part of it into the model's request so the model has something authoritative to work from.

This is not training. Loading a reference file does not permanently teach or retrain the model. It is more like putting selected pages on the desk beside the model before asking the question.

The current reference mode is deliberately straightforward: TGAI includes reference text up to the character limit you choose. Reference-only grounding tells the model to answer from those files or say that the answer is not present. This is not yet a full retrieval-augmented generation (RAG) pipeline that automatically searches a large document library for only the most relevant chunks.

The Context Inspector shows approximately what TGAI is preparing for the next request: system instructions, selected reference material, prior chat history, and your new prompt.

Where do the chat models come from?

TGAI does not create or claim ownership of the language models. The main browser-loadable list comes from the WebLLM / MLC model configuration exposed by the WebLLM runtime. MLC prepares model weights and compiled model libraries so supported models can run efficiently in environments such as WebGPU.

Many model packages are hosted on Hugging Face, a model repository service. The model's Hugging Face page normally includes a model card with information supplied by the model publisher: intended use, architecture, limitations, license information, evaluation notes, and other details.

Why does each model have its own link? TGAI's Model Explorer intentionally keeps a source/project link so you can inspect the actual upstream model instead of relying only on TGAI's short description. For licensing, restrictions, authorship, or model-specific limitations, the upstream model/project documentation is the place to check.

The optional TGAI curated catalog

The external TGAI JSON catalog is an extra layer of human-friendly descriptions and categories. It can include browser models plus reference-only models worth knowing about. Being listed in the curated catalog does not mean a model is loadable in this browser. TGAI compares imported entries with the live WebLLM catalog and shows the loadability status.

This distinction is especially useful for large local coding models. Something such as a Qwen Coder model intended for Ollama or llama.cpp may be valuable research for a local coding workstation while still being far too large, or not packaged correctly, for direct WebLLM loading here.

Text to Image is a separate AI system

The Text to Image workspace is intentionally separate because it does not use WebLLM. It uses ONNX Runtime Web with WebGPU and browser-compatible diffusion-model files. You provide a description, and the image model repeatedly transforms noise into an image.

SD-TurboThe lighter, very fast baseline. It is useful when you want quick local generations and lower resource use.
SDXL-Lightning Q4A heavier SDXL-based path with dual text encoders and a quantized Lightning U-Net. It can produce higher-quality 1024×1024 results but needs substantially more resources.
Stable Diffusion 2.1Kept as a legacy compatibility experiment. TGAI can load the model package, but current WebGPU testing can fail at a U-Net shader operation, so it is not the recommended path.
Seed / passes / sizeThe seed controls the starting random noise. Passes are denoising steps. Larger image dimensions usually require more GPU memory and computation.

Loading an image model can automatically unload the active WebLLM chat model so the two large runtimes do not unnecessarily compete for GPU memory.

Why does TGAI care about the GPU and WebGPU?

AI inference involves a huge amount of matrix math. A graphics processor is very good at doing many calculations in parallel. WebGPU is the browser standard that lets web applications use modern GPU compute capabilities without installing a vendor-specific AI application.

Your browser, operating system, GPU driver, available memory, and the model itself all matter. Two computers running the same HTML file can therefore have very different loading times, generation speeds, and maximum practical model sizes.

TGAI's Probe GPU and Browser/GPU diagnostics are there to make that visible. A failure does not always mean the GPU is too weak; it can also be a browser/runtime/model-kernel compatibility problem.

Model downloads, memory, and browser cache

AI models are much larger than ordinary web-page assets. Small language models may still require hundreds of megabytes or more, and image or larger language models can require multiple gigabytes. The first load is therefore normally the slowest because files must be fetched.

Browser disk cacheDownloaded model files can be kept in browser-managed storage so later sessions may reuse them without downloading everything again.
CPU / JavaScript memoryThe application and runtime may hold model information and temporary tensors in normal process memory.
GPU memoryInference sessions and tensors can occupy dedicated or shared GPU memory while a model is loaded.
Unload vs. deleteUnloading asks the runtime to release active inference resources. Clearing a model cache deletes its stored download. They are different operations.

Request Persistent Storage asks the browser to reduce the chance that cached model files are automatically evicted when storage pressure occurs. The browser can decline the request, and persistence is not the same thing as making a cloud backup.

What “local-first” means here

The important distinction is between downloading software/model resources and performing inference. TGAI normally needs network access the first time it loads WebLLM, ONNX Runtime Web, tokenizers, or model files because those resources are hosted elsewhere. Once the necessary resources are present and usable, the actual supported model inference happens in your browser on your machine.

TGAI itself does not need a hosted prompt/inference server for these local model paths. Local reference files are read by the browser for use in the local application; TGAI does not intentionally upload those files to an AI inference service.

Local-first does not mean “no network traffic ever.” Opening the application or loading a model can contact CDNs, GitHub/Hugging Face/model hosts, or other upstream locations used for runtime and model files. If you need a strict offline environment, preload/copying all dependencies would be a separate deployment exercise.

Diagnostics & Logging workspace

This section is the dashboard for what TGAI sees from the browser. It reports WebGPU availability, adapter details, approximate memory information when the browser exposes it, the currently loaded chat model, reference size, model load/generation timing, tokens per second, and runtime messages.

The log is especially useful when a model does not load. A large AI model can fail for very different reasons: a missing file, browser storage issue, unsupported GPU feature, incompatible ONNX operator/kernel, device loss, out-of-memory condition, or a runtime/model packaging problem.

The image workspace also has targeted compatibility diagnostics because image-generation ONNX graphs can exercise very different GPU kernels than language models.

Common troubleshooting

  • A model is listed but Load Model is unavailable: it may be a reference-only catalog entry rather than a model exposed by the current WebLLM built-in catalog.
  • First load takes a long time: watch the progress/status. Multi-gigabyte model downloads are normal for heavier models.
  • The model used to work but now looks disposed: browsers can reclaim a WebGPU device/runtime after long idle periods. Reload the model; TGAI tries to preserve the unsent prompt.
  • Generation is extremely slow: try a smaller model, lower-memory quantization, smaller image size, or fewer supported image passes. Check that the browser actually selected the intended GPU.
  • Image generation fails during the first U-Net pass: enable Image Compatibility Diagnostic mode and inspect the diagnostic result/runtime log.
  • Cached models disappeared: browser storage is managed by the browser and may be cleared manually or evicted under storage pressure. Persistent Storage can reduce, not eliminate, that possibility.
  • The model starts repeating the same line or short block: very small models can fall into repetition loops. TGAI v0043 watches streamed output for an obvious repeated-line pattern and automatically interrupts it.
  • You press Stop: TGAI now waits for WebLLM to acknowledge/finish the interrupted stream before declaring the model ready again. This avoids abandoning a live stream and then sending a new request into a runtime that is still busy.
  • The browser freezes: very large models can overwhelm available memory. Start with a smaller model and unload other AI runtimes before retrying.

Local Text-to-Image Lab — SD-Turbo / SDXL-Lightning / WebGPU ONNX Runtime Web ↗

This workspace uses a browser-local diffusion runtime separate from WebLLM chat. TGAI keeps only the active image inference sessions resident in memory. Switching image models releases the prior image sessions; changing dimensions rebuilds only the spatial U-Net/VAE sessions while retaining the reusable text encoder. Model files are kept in browser disk cache. The image workspace keeps the working SDXL-Lightning Q4 path and provides contextual help throughout the lab using native browser tooltips and accessibility labels. The persistent-storage controls now explain that persistence only reduces automatic browser cache eviction; it does not upload or sync model files.

Use Diagnostic for first-pass WebGPU compatibility testing. It does not change diffusion math or silently fall back to another backend.
